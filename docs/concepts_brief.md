# ShopHub Multi-Tenant Support Assistant

* **Author:** yeshwanthgowda-dev
* **Date:** 2026-11-18

## Overview

ShopHub hosts many independent merchant stores. Merchant support staff chat with an assistant that answers questions about their own store's orders and can propose refunds or cancellations. The task (see `shophub.pdf`, R0–R11) is to build this as a LangGraph orchestrator plus an orders sub-agent exposed over A2A JSON-RPC, backed by a small mock store API. It must run offline with a scripted fake LLM, keep merchants strictly apart, ignore instructions hidden in customer notes, keep customer emails and phones away from the model, and never refund or cancel without an explicit human approval.

The central design idea: the model has no authority. It can read and it can propose. Only ordinary code, run after an approval, can change an order. If an injection fools the model, the worst outcome is a bad proposal that a human can reject.

The code goes on the separate `code` branch. The `plan` branch holds design files only: this brief, `EXECUTION.md` (build runbook) and `DESIGN.md` (living draft of the R11 deliverable). Time budget is about 24 hours. The author wants all of R0–R11 done and wants to understand every line, so each module follows design, code, test, walkthrough.

## Analysis

Seven review lenses ran on the plan. Their findings, deduplicated:

**Blockers that changed the design**

1. *The model might reach refund or cancel directly.* If the orchestrator binds every skill the agent card lists, an obedient model can execute a refund and R5 means nothing. Fix: the model gets read tools plus `propose_refund` and `propose_cancel`. Proposal tools never call write endpoints. `/approve` runs execution in non-LLM code, using the approver's own token. The orchestrator uses an explicit skill allowlist, and the sub-agent port is not published to the host.
2. *The token can leak into checkpoints.* LangGraph may copy values from per-call config into checkpoint metadata (reviewer recall, unverified). Fix: a 15-minute spike first; carry the token outside `configurable` (a context variable or per-request closure); turn tracing off; add a test that scans the SQLite files for a planted token, with a positive control.
3. *The token path over A2A was unspecified.* It travels only in the HTTP `Authorization` header, set per request, never as a shared client default, never in params, logs, or events.
4. *Proposal state had two owners and no atomic claim.* Fix: a small `proposals` table with one atomic claim query, interrupt carrying only the proposal id, server-filled merchant and amount, and a re-check of order state at approval time.
5. *"Checkpoint stores only thread_id and merchant" was wrong.* A checkpoint stores full graph state. The invariant becomes: no token, no raw PII and no raw note text enters state, config or checkpoint.
6. *Thread ownership.* Thread ids are generated by the server. Every endpoint checks the token's merchant against the thread's merchant. Unknown and foreign threads return the same 404.
7. *R10 says compose starts "the database."* The plan used an in-memory store. Decision: SQLite on a named volume owned by the orchestrator. DESIGN.md says plainly that this volume is the database.
8. *Module order had no early test path.* The fake LLM was last. It moves to step 0, and a thin end-to-end slice lands by about hour 8.
9. *Interface contracts were missing.* `EXECUTION.md` defines routes, the error table, the SSE event schema, the A2A contract and the proposal record so a coding assistant doesn't invent them.

**Major findings (summarised)**

* The fake LLM must be a real `BaseChatModel` that picks actions by rule from message history, streams, and has an adversarial "obeys injections" mode. That mode proves the deterministic layers work, not the model's behaviour.
* The provenance check on proposals is weak when ids appear in lists. It is tightened to "the id must be in the latest human message," and is the first layer to drop to documentation if time runs short.
* Text the user types (an email, a phone number) also reaches the model. A deterministic pre-model step handles it and returns a fixed refusal.
* Redaction needs two ends: a typed allowlisted response from the sub-agent, re-validated and re-scrubbed in the orchestrator.
* Normalise the legacy `200 + status:false` envelope in exactly one place, and make "not found" and "belongs to another merchant" produce one identical outcome.
* Use `a2a-sdk` (author's decision, pinned version) with a 90-minute timebox and a hand-rolled fallback. The SDK's task store must not persist the token. The sub-agent is deterministic with no LLM, which removes a prompt-injection surface.
* Use `AsyncSqliteSaver` entered once in the FastAPI lifespan, because SSE needs the async graph.
* Time estimates total about 21–25 hours including buffer, with only 1–3 hours of slack. The rule: a module over 50% late takes its simpler variant, and the cut order is written down now.

**Resolved contradictions:** token forwarded yet never stored (client re-sends on resume); names needed for lookup yet PII (author's decision: drop `customer_name` from all output, keep it only as a server-side search filter, use opaque labels when several customers match); notes useful yet untrusted (omit by default, separate tool, wrap and flag); strong guardrail yet offline (capability design bounds the damage, so detection can stay simple).

**Ideal Final Result:** a clean clone runs `docker compose up` and `pytest` offline with no key; the eval prints per-case pass/fail; tenancy, injection resistance and restart survival hold by construction and tests assert that construction against the real mock store.

## Security Invariants

Tests cite these by number.

1. The bearer token is never written to state, checkpoint, logs, SSE events, A2A params, or any database file.
2. A token's merchant is the only source of tenant identity. A null merchant fails closed at chat, approve and sub-agent.
3. Another merchant's order, unknown order and foreign thread are indistinguishable to the caller.
4. Email and phone values never appear in any model input, checkpoint or SSE event.
5. Text from `customer_note` is never in the model input unless requested, and then only wrapped as untrusted data.
6. The model cannot execute a refund or cancel. Only `/approve` can, with a pending, unexpired, single-use proposal whose merchant equals the approver's merchant and the thread's merchant.
7. The legacy `200 + status:false` envelope is always treated as a failure.
8. Order state is re-checked at approval time. A changed state returns as data, not as an executed action.
9. A proposal is created only after a verifier that sees human messages and no tool output confirms the user asked for that exact action. A failed or ambiguous check ends the run with a fixed template reply, and the user can ask again in the next message.
10. Customer names never appear in tool output or model input. A name typed by the user is used only as a search filter inside the sub-agent.
11. The merchant is derived from the token alone. A caller-supplied merchant claim is only compared against it, and a mismatch is rejected.
12. An order has at most one pending proposal. Proposal state lives in the orchestrator's `proposals` table, and a proposal never changes the order's status in the store.

## Goals vs. Non-Goals

* **In-Scope Goals:** R0–R11 in full; per-case eval harness; README and DESIGN.md with honest cuts; real commit history; AI-assistant disclosure; one explanation walkthrough per module.
* **Out-of-Scope Non-Goals:** Google login and any OAuth; Postgres and database-level RLS; staff dashboard; MCP (noted in DESIGN.md only); a local or hosted injection classifier (documented, not built); sub-entities under one merchant; choosing a stretch item (S1, S2 or S3 is decided after R11); web UI.

## Alternatives Weighed

* **Google login for tokens.** Rejected by author after review: OAuth is "not graded," needs the network, breaks clean-clone runs, and does not solve where the token is kept.
* **Cookies for the token.** Rejected: the clients are scripts, cookies add forgery risk, and R3 says the assistant must not cache credentials.
* **Refusing user queries that mention injection.** Rejected: the injection sits in customer note data, not the staff query. Refusing would let an attacker block staff by planting a note.
* **Hosted classifiers ("Jev", "Decisions API").** Rejected: not verifiable from public sources, and they fail the offline requirement.
* **Local classifier (Prompt Guard, DeBERTa).** Deferred: needs PyTorch (1–2 GB in the image) and baked-in weights. Listed as a flagged future option.
* **`order_exists: true` key on the legacy lookup.** Rejected: it tells staff that another merchant has that order, an existence leak.
* **Database-level RLS plus dashboard.** Deferred: RLS only helps if orders live in Postgres, and R0 specifies an in-memory store. Noted for DESIGN.md.
* **`IN_REVIEW` order status.** Rejected after review (author agreed): it changes the store's six-status model, needs a write endpoint before approval, and leaves an order stuck if the proposal expires. A uniqueness rule on pending proposals gives the same protection.
* **Merchant id as identity in the sub-agent.** Rejected: a caller-asserted id lets a bug or compromised orchestrator claim any merchant. Kept only as a claim to verify.
* **Keeping `customer_name` in tool output.** Rejected by author: dropping it removes a PII field and a second injection channel. Cost: "who ordered 1042?" cannot be answered.
* **Postgres in compose.** Deferred: SQLite is allowed with justification, and no server is available. Swap path documented.
* **Hand-rolled A2A.** The review preferred it (SDK churn, boilerplate). Rejected by author: the SDK is simpler to use. Kept as the fallback if the SDK costs more than 90 minutes.
* **Quarantined second LLM to summarise notes.** Deferred as future work.
